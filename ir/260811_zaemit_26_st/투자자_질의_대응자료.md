# Part 1. 기술·인력 (Technology & Talent)

## Q1-1. 글로벌 AI 기업으로부터 침범당하지 않을 AI 개발 인력풀이 있는가

### ① 한 줄 답변
"우리는 프론티어 모델과 '모델 성능'으로 경쟁하지 않습니다. 위븐의 해자는 AI 생성 레이어 **위**에 있는 오케스트레이션·운영 레이어이며, 이 레이어를 설계·운영할 수 있는 인력과 검증된 산출물(특허, 논문, 자체 모델 운영 실적)을 이미 보유하고 있습니다."

### ② 논리 전개

**(1) 질문의 전제를 재정의합니다 — "침범"의 방향이 다릅니다.**
- OpenAI, Anthropic, Google이 더 좋은 모델을 낼수록 위븐의 원가는 **내려가고** 산출물 품질은 **올라갑니다**. 프론티어 모델은 위븐의 경쟁자가 아니라 공급자입니다.
- 실제로 위븐은 이미 멀티 벤더 구조를 운영 중입니다: 생성 파이프라인은 프론티어 API(단계적 에스컬레이션 구조), 고빈도 운영 루프는 자체 호스팅 모델 Apollon(Qwen3.6-35B-A3B 기반)으로 이원화되어 있습니다. 특정 벤더에 종속되지 않는 하이브리드 라우팅이 아키텍처 차원에서 구현되어 있습니다.
- 글로벌 AI 기업이 침범하기 어려운 이유는 인력의 '스펙'이 아니라 **축적된 도메인 자산**입니다: 한국·일본 웹 제작 시장에 특화된 섹션 카탈로그, RAG 파이프라인, 운영 자동화 루프, 그리고 GMO 페파보 같은 채널 파트너십은 모델 성능으로 복제되지 않습니다.

**(2) 인력의 글로벌 경쟁력은 '커리어 나열'이 아니라 '검증 가능한 산출물'로 답합니다.**

| 검증 가능한 산출물 | 내용 | 의미 |
|---|---|---|
| 특허 | 멀티에이전트 아키텍처 관련 특허 출원 [출원번호 확인 필요] | 기술의 법적 방어선 |
| 학술 논문 | Retrieve–Verify–Escalate 프레임워크 (셀프호스팅 모델의 신뢰성 있는 멀티에이전트 오케스트레이션) — SCI급 저널 투고 [상태 확인 필요] | 기술의 학술적 검증 |
| 자체 모델 운영 | Apollon: Qwen3.6-35B-A3B 기반 LoRA 파인튜닝, vLLM 멀티 LoRA 서빙, 프로덕션 투입 | "논문이 아니라 실전"이라는 증거 |
| 멀티에이전트 시스템 | DAG 기반 오케스트레이터(plan→gather→synthesize), 4개 전문 에이전트(WebGen/ImgGen/Dev/Ops) 상용 운영 | 글로벌에서도 상용 사례가 드문 영역 |
| MCP 생태계 | Zaemit MCP 툴셋 구축 — Claude 등 외부 AI에서 재밋 사이트를 직접 제작·운영 | AI 네이티브 배포 채널 선점 |

**(3) 창업자 리스크에 대한 선제 방어**
- 대표(김정환): 고려대학교 디지털경영 박사, IT 경력 20년+, 자체 모델 파인튜닝부터 사업 전략까지 풀스택 커버. 창업자가 기술의 최종 의사결정자라는 점은 초기 단계에서 리스크가 아니라 실행 속도의 원천입니다.
- 핵심 개발 인력 현황: [확인 필요 — 인원수, 각자의 역할, 대표 커리어 1줄씩 표로 작성. 예: "OO — 백엔드 리드, 前 OO 재직, 재밋 오케스트레이터 설계 참여"]

### ③ 증빙 자료
- 특허 출원서 사본, 논문 원고(투고 확인 메일 포함), Apollon 운영 대시보드 캡처(추론량·비용 지표), 조직도 및 핵심 인력 이력 요약

## Q1-2. 내부 인력풀은 충분한가 — 리텐션 패키지 세팅

### ① 한 줄 답변
"핵심 인력에 대한 스톡옵션 부여를 완료했고 [확인 필요], 직무발명보상규정을 통해 특허 성과가 개인 보상으로 연결되는 체계를 갖추고 있습니다 [규정 유무 확인 필요 — 없다면 이번 라운드 전 제정 권장]."

### ② 논리 전개

**(1) 리텐션의 3층 구조로 답변합니다.**

| 층위 | 수단 | 현황 |
|---|---|---|
| 지분 | 스톡옵션 (부여 수량·행사가·베스팅 조건) | [스톡옵션 부여 내역서와 연동 — 자문께 별도 제출 예정인 자료 인용] |
| 금전 보상 | 직무발명보상규정 — 출원 보상 / 등록 보상 / 실시(수익화) 보상 3단계 | [규정 제정 여부 확인 필요. 미제정 시: "8월 중 이사회 결의로 제정 예정"으로 답변] |
| 비금전 보상 | 논문 공저 기회, 특허 발명자 등재, 기술 브랜딩(컨퍼런스 발표) | 이미 실행 중 — RVE 논문, 특허 출원에 팀원 참여 |

**(2) "충분한가"에 대한 정직한 답변 구조**
- 현재 인력은 현 단계(제품·초기 매출)에는 충분하나, 5개년 로드맵의 Year 2 이후 확장에는 채용이 필요합니다. 이것이 바로 이번 라운드 자금의 용처(Use of Proceeds) 중 하나입니다.
- 투자자가 원하는 답은 "지금 다 있다"가 아니라 "무엇이 부족한지 정확히 알고, 투자금으로 누구를 뽑을지 정해져 있다"입니다. → Q1-4의 채용 계획과 연결.

### ③ 증빙 자료
- 스톡옵션 부여 계약서, 주주명부(Fully Diluted), 직무발명보상규정(또는 제정 일정), 취업규칙 내 겸업·경업금지 조항

## Q1-3. 향후 5년 기술 로드맵 — 무엇을, 누가, 글로벌 경쟁력은

### ① 한 줄 답변
"로드맵의 종착점은 '웹사이트를 만들어주는 AI'가 아니라 '웹사이트를 대신 운영하는 AI(AI Site Operator)'이며, 생성은 경쟁이 치열하지만 운영 자동화는 아직 글로벌하게 비어 있는 자리입니다."

### ② 논리 전개

**(1) 5개년 기술 로드맵 (Draft — 연도별 수치·과제명은 대표님 확정 필요)**

| 단계 | 기간 | 핵심 과제 | 담당 | 성공 지표(예시) |
|---|---|---|---|---|
| Phase 1: 생성 완성도 | 2026 하반기 | 멀티에이전트 생성 파이프라인 안정화, Apollon 스타일 파인튜닝(zaemit style) 고도화, MCP 툴셋 정식화 | 대표 + 개발팀 [명시 필요] | 생성 1회 성공률, 재생성률, 건당 추론 원가 |
| Phase 2: 운영 자동화 | 2027 | Ops 에이전트 확장 — 콘텐츠 갱신·SEO·게시판 운영 자동 루프, 고빈도 루프의 Apollon 전환율 확대 | | 사이트당 월 자동 운영 액션 수, 운영 원가 |
| Phase 3: 플랫폼화 | 2028 | 에이전시·리셀러용 화이트라벨/OEM 아키텍처(일본 GMO 모델의 일반화), 파트너 API | | OEM 파트너 수, 파트너 경유 사이트 수 |
| Phase 4: 데이터 해자 | 2029 | 운영 데이터 기반 도메인 특화 모델 라인업(업종별 LoRA), 성과 예측·개선 제안 자동화 | | 업종별 모델 수, 운영 성과 개선율 |
| Phase 5: 자율 운영 | 2030 | 완전 자율 AI Site Operator — 목표(매출·문의 수) 기반 사이트 자율 개선 | | 자율 운영 사이트 비중 |

**(2) "누가 하는가"**
- 아키텍처·모델 전략: 대표 직접 리드 (특허·논문의 발명자/저자로 검증됨)
- 구현: 현 개발팀 [인원·역할 확인 필요] + Phase 2부터 ML 엔지니어 1~2명 채용 (Use of Proceeds)
- 학술 자문: [자문 교수·기관이 있다면 기재 — 없으면 생략]

**(3) 글로벌 경쟁력의 근거 — 3가지 각도**
- **포지셔닝**: Wix·Framer·Lovable 등 글로벌 플레이어는 '생성'에서 경쟁 중이고, 운영 자동화 루프를 SMB 웹사이트에 상용 적용한 사례는 드뭅니다. 경쟁사 대비표 [작성 필요 — Higgsfield 아키텍처 분석 자료 재활용 가능: 사이트별 격리 서버리스 vs 위븐의 공유 멀티테넌트 구조가 '지속 운영'에 유리하다는 논리]
- **원가 구조**: 고빈도 운영 루프를 자체 호스팅 Apollon으로 처리 → 사이트 수가 늘어도 운영 원가가 선형으로 늘지 않는 구조. TCO 분석 자료 보유.
- **검증**: 특허 + SCI급 논문 + 일본 대기업(GMO 페파보) 파트너십 — 기술이 내부 주장이 아니라 외부 검증을 통과했다는 증거.

### ③ 증빙 자료
- 기술 로드맵 1페이지 도식, 아키텍처 다이어그램, 경쟁사 비교표, TCO 분석 요약

# Part 2. GTM (Go-To-Market)

## Q2-1. 누가, 어디서부터 마케팅을 시작하는가

### ① 한 줄 답변
"B2C 대중 시장이 아니라 **웹을 업으로 하는 전문가(에이전시·프리랜서·인하우스 마케터)**부터 시작합니다. 이들은 1명이 수십 개 사이트를 만드는 멀티플라이어이고, 이미 국내 채널(대표 개인 브랜딩·세미나)과 일본 채널(GMO OEM)이 열려 있습니다."

### ② 논리 전개

**(1) 시장 진입 순서 (Beachhead → 확장)**

| 순서 | 시장 | 채널 | 상태 |
|---|---|---|---|
| 1 | 국내 전문가 시장 (에이전시·프리랜서) | 대표 Threads 브랜딩, 세미나, 크몽 등 프리랜서 마켓 접점 | 진행 중 — 7월 Zaemit.ai 오픈, 구축 프로젝트 실적 축적 중 |
| 2 | 일본 | GMO 페파보 OEM (수익배분 구조 합의) — 구축 후 월 이용료로 전환되는 IYP 모델 | 계약 [단계 확인 필요] |
| 3 | 글로벌 셀프서브 | Microsoft 마켓플레이스, MCP 통한 AI 네이티브 유통(Claude 등에서 직접 사이트 제작) | 준비 중 |
| 4 | 동남아 | 말레이시아 [파트너·진입 방식 확인 필요] | 탐색 |

**(2) "왜 전문가부터인가" — 투자자용 논리**
- 전문가 1명 = 사이트 N개 = 구독 N건. CAC는 1명분, LTV는 N배. 이것이 구독 곡선을 기하급수로 세우는 구조적 장치입니다.
- 전문가는 도구 전환 비용에 민감하지만, 한번 정착하면 이탈률이 낮고 리셀러(공급채널)로 진화합니다 — 수익모델 4개 축 중 '공급채널'과 직결.
- 자문께서 제안하신 "하반기 구독 곡선 세우기"와 정합: 전문가 채널이 가장 짧은 시간에 구독 건수를 쌓는 경로입니다.

### ③ 증빙 자료
- 채널별 퍼널 현황(방문→가입→유료), GMO 계약/협의 문서, MCP 사용 실적

## B. 예상 후속 질문 (2차 방어선)

1. **"Apollon이 프론티어 모델보다 성능이 낮은데 왜 자체 호스팅인가?"**
   → 성능이 아니라 원가·지연시간·데이터 주권의 문제. 고빈도 운영 루프는 요구 성능이 한정적이며, 이 구간을 자체 모델로 처리해야 사이트 수 증가 시 마진이 방어됨. 품질이 필요한 구간은 프론티어로 에스컬레이션(Retrieve–Verify–Escalate가 바로 이 설계).

2. **"핵심 개발자가 이탈하면?"**
   → 아키텍처·프롬프트·파인튜닝 파이프라인이 문서화·특허화되어 개인 의존도가 구조적으로 낮음 + 스톡옵션 베스팅 + 직무발명보상. [문서화 수준 확인 필요]

3. **"월 2배 구독 성장의 근거는?"**
   → 절대 수치가 작은 초기 구간의 목표이며, 전문가 1명당 N개 사이트 구조가 배수 성장을 만드는 장치. 3개월 실적으로 증명하겠다는 커밋으로 답변.

4. **"GMO가 직접 만들면 되지 않나?"**
   → OEM 계약의 수익배분 구조 자체가 GMO의 'buy' 결정 증거. 멀티에이전트 오케스트레이션은 웹호스팅사의 핵심 역량 밖이며, 특허·논문이 진입장벽.
